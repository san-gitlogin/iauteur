## C · `uv pip compile` — and the thing that catches everyone

`requirements.in` contains one word: `rich`.

```console
$ uv pip compile requirements.in
Resolved 4 packages in 64ms
# This file was autogenerated by uv via the following command:
#    uv pip compile requirements.in
markdown-it-py==4.2.0
    # via rich
mdurl==0.1.2
    # via markdown-it-py
pygments==2.21.0
    # via rich
rich==15.0.0
    # via -r requirements.in
```

**It printed. It did not write anything.** Without `-o` the compiled output goes to stdout,
and a beginner who runs the documented command and then looks for `requirements.txt` finds
nothing. That is a real trap and it belongs in chapter 12.

The `# via` comments are worth a beat of their own: every pinned line records WHO asked for
it, so `# via rich` and `# via -r requirements.in` distinguish a dependency from a request.

```console
$ uv pip compile requirements.in -o requirements.txt
Resolved 4 packages in 8ms
…same content, written to the file this time…

$ uv pip sync requirements.txt
Resolved 4 packages in 4ms
Checked 4 packages in 0.66ms
```

## D · `uv tool install` — the bolted-down tool

```console
$ uv tool install ruff
Resolved 1 package in 456ms
Downloading ruff (10.1MiB)
 Downloaded ruff
Prepared 1 package in 2.00s
Installed 1 package in 623ms
 + ruff==0.16.4
Installed 1 executable: ruff
warning: `/…/sandbox/uvhome/bin` is not on your PATH. To use installed tools, run
`$env:PATH = "/…/sandbox/uvhome/bin;$env:PATH"` or `uv tool update-shell`.
```

**That warning is the beat.** Every beginner installs a tool and then cannot run it, and uv
tells you exactly why and hands you the fix in the same breath.

```console
$ uv tool list
ruff v0.16.4
- ruff

$ uv tool dir
~/AppData/Roaming/uv/tools          # Unix: ~/.local/share/uv/tools

$ ls "$(uv tool dir)/../bin"
ruff.exe                            # ONE executable — the shim, not the package

$ uv tool upgrade --all
Nothing to upgrade
```

And the misunderstanding this chapter exists to kill:

```console
$ uv pip show ruff
warning: Package(s) not found for: ruff
```

**Installing a tool does not make its modules importable in your project.** The tool lives
in its own environment; `uv pip show` is looking in yours, and ruff genuinely is not there.

```console
$ uv tool uninstall ruff
Uninstalled 1 executable: ruff
```

## G · `uv sync` is `--exact`, and it will delete things

Installed `typer` behind uv's back with `uv pip install typer`, then ran a plain `uv sync`:

```console
$ uv sync
Resolved 13 packages in 1ms
Uninstalled 3 packages in 47ms
 - annotated-doc==0.0.5
 - shellingham==1.5.4
 - typer==0.27.1
```

**`uv sync` REMOVED three packages nobody asked it to touch.** That is the documented
`--exact` default doing exactly what it says: the environment is made to match the
lockfile, and anything else is an extra. This is the single most surprising uv behaviour
for a pip user and chapter 09 must show it happening rather than describe it.

```console
$ uv lock --check
Resolved 13 packages in 1ms          # silence means up to date

$ uv lock --upgrade-package rich
Resolved 13 packages in 152ms
```

## H · version, build, and verifying the result

```console
$ uv version
hello-world 0.1.0

$ uv version --bump minor --dry-run
hello-world 0.1.0 => 0.2.0
```

`--dry-run` prints the arrow and changes nothing. Show the arrow.

```console
$ uv build
Building source distribution...
Building wheel from source distribution...
Successfully built dist\hello_world-0.1.0.tar.gz
Successfully built dist\hello_world-0.1.0-py3-none-any.whl
```

```
dist/
├── .gitignore                              1 byte
├── hello_world-0.1.0.tar.gz              760 bytes
└── hello_world-0.1.0-py3-none-any.whl   1631 bytes
```

Real filenames, real sizes. **The wheel is built FROM the sdist** — the second line of the
output says so, and that ordering is a beat on its own.

⚠ **A verification command that does NOT work.** The obvious check fails:

```console
$ uv run --with rich --no-project -- python -c "import rich; print(rich.__version__)"
AttributeError: module 'rich' has no attribute '__version__'
```

`rich` exposes no `__version__`. Use an import that proves the package works instead —
`python -c "import rich; rich.print('[bold]ok[/bold]')"` — and do not put the failing one
on screen as if it succeeded.
