The Video Factory
How a topic becomes a rendered video

This is a Remotion (React) "video factory". You never hand-draw frames. You write a JSON spec that describes scenes; Remotion turns that JSON into 1920×1080 and 1080×1920 video. This page explains every moving part, how the Studio timeline appears, where the 30 designs live, and what we plan to build next.

1 · The mental model

Three sentences hold the whole system together:

CONTENT

The JSON is the movie. A spec in topics/<slug>/long.json lists scenes, each with a type, narration, a durationFrames, and a data object. Change the JSON → change the video.

LOOK

The theme + design pack skin it. brand.theme picks colors/fonts; brand.design picks a component "grammar". The same JSON renders in 30+ looks without changing a word.

MOTION

Everything is a function of the frame. No timers, no CSS animation. Given frame N, every pixel is deterministic — that's what makes it renderable and reproducible.

The key insight for your bigger goal: AI is the director + editor. It picks the topic's angle, writes narration, chooses scenes, times them to words, and picks a look. The components are its vocabulary. Richer components + richer animation = the AI can compose more varied "films" — which is exactly what phase 2 (this task) is about.

3 · How the Studio timeline appears in the browser

When you run npm run dev, Remotion Studio opens at localhost:3000. The timeline you see is not hand-authored — it is generated at load time from your topic JSON. Here is the chain that produces it:

sequenceDiagram autonumber participant Dev as You (npm run dev) participant R as Root.tsx (RemotionRoot) participant TI as topicsIndex.ts (auto-gen) participant MC as MainComposition participant TP as ThemeProvider participant IN as Inner (scene loop) participant SC as Scene component Dev->>R: Studio boots, reads RemotionRoot R->>TI: import topics[] (slug, long, shorts) loop for every topic R->>R: register <Composition> wide-dark / wide-light / short-dark / short-light + thumb/cover stills end R->>R: also register Gallery + showcase-<design> (one topic under all 30 packs) Note over R: Studio's left panel = this list of Compositions Dev->>MC: click a composition → Remotion mounts it at frame 0 MC->>TP: apply themeOverride (dark/light) + background override MC->>IN: render Inner(spec) IN->>IN: walk scenes[], accumulate "from" = running frame offset loop each scene IN->>IN: wrap in <Sequence from=offset durationInFrames=scene.durationFrames> IN->>SC: resolveScene(design,type) ?? registry[type] ?? Unknown SC-->>IN: draws using useCurrentFrame() (LOCAL to the Sequence) end IN->>IN: overlay Watermark + design Chrome above all scenes Note over IN: The timeline bar = concatenated Sequences.
Each Sequence's width = its durationFrames.
The timeline is literally a stack of <Sequence> blocks laid end to end. Scene 1 occupies frames 0…d1, scene 2 occupies d1…d1+d2, and so on (specDuration sums them, plus the optional cover). Inside a Sequence, useCurrentFrame() resets to 0, so each scene animates relative to its own start. Word anchors (atWord) become frames via wordToFrame = (word-1)×12 at 150 wpm.

Because every frame is a pure function of its frame number, Remotion can render frames in parallel and always get identical output. That determinism is why "no CSS keyframes / no timers / no Math.random without a seed" is a hard rule.

6 · What the src/designs/ folder actually does

A design pack is a genuinely different component grammar — not just recolored. Each of the 30 packs is a folder with three files:

primitives.tsx

Pack-specific building blocks (e.g. cyberpunk's chamfered neon CyberPanel, GlitchHeadline) plus a full-frame *Chrome overlay (scanlines, grain, vignette, corner ticks).

scenes.tsx

Re-implements up to 5 scene types in the pack's style, reading the same theme tokens (useTheme), scale (useScale), semantics (useSem) and word anchors as core.

index.ts

Exports a registry (type → component) and the Chrome. Both are wired into src/designs/index.ts.

The core limitation this project set out to fix: every one of the 30 packs overrides only these 5 scene types — HOOKSTAT_PANELSSTEP_FLOWLIST_BUILDSTAT_CALLOUT. The other 9 types always fall back to the identical core component, only recolored: TITLE_CARDCONCEPT_DIAGRAMRECAPOUTRO_CTACHAT_MOCKUPQUOTE_SPOTLIGHTSPLIT_PATHSBAR_COMPARECHANNEL_CARD. So diagrams, quotes, the only bar chart, and chat mockups look the same in all 30 designs.

7 · Anatomy of one scene (real example)

The JSON the AI writes 
{
  "id": "s03",
  "type": "SPLIT_PATHS",
  "narration": "Old search hands you
     a list of blue links...",
  "durationFrames": 354,
  "background": "zoneA",
  "data": {
    "headline": "One query, [two results.]",
    "headlineColor": "orange",
    "center": {"title":"your search",
               "color":"blue","atWord":2},
    "left":  { "title":"Old search", ... },
    "right": { "title":"AI search", ... },
    "source": "Semrush, Mar 2026"
  }
}
How it becomes pixels
  1. type → resolveScene picks the component (core SplitPaths here — no pack overrides it).
  2. data.* → fills the component's slots (headline, two path cards, center node, source footer).
  3. [two results.] → the bracketed phrase gets the accent color (exactly one per headline).
  4. atWord:2 → element enters at frame (2-1)×12 = 12 — "show it when you say it".
  5. headlineColor:"orange" → semantic meaning (tension/choice), mapped to the theme's hue via useSem.
  6. durationFrames:354 → the Sequence width; ≈ words×12+30.

Semantic colors mean things: green=works red=broken blue=info/tech purple=AI/agent orange=tension yellow=cost

9 · Why two videos still feel like the same film

Update — largely resolved. The gaps below were the original diagnosis. Since then the core scene library grew from 14 to 23 types: real diagrams (flow/sequence/block/tree/hub with animated connectors + arrowheads), dynamic text (KINETIC_TEXT, 8 FX), media (PHOTO Ken-Burns with real sourced images, SOUND_WAVE, CAROUSEL), plus REVEAL, LOGO_REVEAL, CREDITS_ROLL and SUBSCRIBE_REMINDER. A scene.fx layer adds letterbox / vignette / shake / particle-burst, and two animated backgrounds (matrix-rain, noise) joined the set. The linter + critic now enforce an anti-monotony law. Proof: the how-llms-work video below leans on all of it.
a · Scene variety is shallow. 5 of ~14 scene types are pack-aware; 9 are identical everywhere. Charts, diagrams, quotes, chat all render one way.
b · The motion vocabulary is tiny. Four helpers (fadeUp / springPop / stackIn / counterValue) + one cross-fade. Every entrance, emphasis and transition looks the same regardless of design or topic.
c · No data-viz, no code window. The only "chart" is BAR_COMPARE. There is no line/area/donut/progress-ring/timeline/quadrant, and no editor/terminal that types code and shows output — a huge miss for technical topics.
d · The screenplay is fixed. Scene order & pacing are effectively one template per format, so timelines feel stamped from a mold instead of edited.

10 · The plan — what we build next

All of it is reusable template infrastructure, respecting the Design Contract (Three Guards, ×scale, both-aspect proofs, deterministic motion). Proposed in five workstreams:

WS-1 Motion library — grow src/anim.ts into src/motion/: entrances (slide, mask-wipe, clip-reveal, blur-in, scale-pop), emphasis (pulse, shake, highlight-sweep), text reveals (typewriter, word/char stagger), number odometer & count-up variants, path-draw, camera push/parallax, and stagger utilities. Theme-aware, ×scale-safe, clamped.
WS-2 Chart / data-viz primitives — a src/charts/ kit: animated line, area, grouped/stacked bars, bar-over-time (race), donut/pie, progress rings, comparison/before-after, timeline, scatter/quadrant. New SceneData fields + new scene types (e.g. LINE_CHART, DONUT, TIMELINE, QUADRANT), fully theme-colored and budget-linted. Reference grammar borrowed from the 81-template RVE library (chart set) but rebuilt to our contract.
WS-3 Code-window component — a realistic editor/terminal scene (CODE_WINDOW): typed code with theme-driven syntax colors, a run/output state, and a typing animation. Great for technical topics; styled per theme (mock-window chrome for moderndark, phosphor for terminalcli, etc.).
WS-4 Deepen the packs — give the currently-core-only scene types pack-aware variety where it matters most (CONCEPT_DIAGRAM, QUOTE_SPOTLIGHT, BAR_COMPARE) and add new scene archetypes so the screenplay has more building blocks.
WS-5 Screenplay system — presets for scene order + pacing (e.g. "explainer", "listicle", "versus", "deep-dive", "hype-launch") the director can pick from, plus rhythm/emphasis-beat guidance. Enables different component mixes per video and per pack, so no two timelines feel templated.
Verification at every step: tsc --noEmit clean · lint-all.mjs green · proof stills at BOTH 1920×1080 and 1080×1920 · existing renders never broken (additive first). New themes/design names get added to DARK_THEMES in both Root.tsx and lint-spec.mjs.

11 · The 81-template coverage + the critic

All 81 real .tsx files were read (not just the README), and each mapped in scripts/catalog.mjs (RVE_81). Their distinctive techniques were ported faithfully into our deterministic, theme-aware contract — note: 7 of the originals use Math.random() or CSS @keyframes (non-deterministic / Next.js-only) and were reauthored as pure useCurrentFrame functions. The library is complete — every high- and medium-value template is built and proofed in both aspects; only two purely-decorative one-offs (subscribe-reminder overlap, film-burn) are optional, and even subscribe-reminder now ships as a scene.

The critic — a design review for every scene

scripts/critique.mjs reads a spec and reviews each scene on ten dimensions — the same ones a design manager would ask about:

DimensionWhat it checks
ContextIs this the right component for the beat's intent (chart-by-intent)?
DisplayMiddle-band layout: headline top, content centred, source bottom, edges clear.
AspectHow it reflows wide (1920×1080) vs vertical (1080×1920).
ColourSemantic meaning; adapts to dark theme AND light twin via useSem.
Fontsdisplay / body / mono roles; ≤3 families per frame.
MotionEntrances 12–18f, anchored to atWord, one focus per frame.
AssetsEvery icon/logo/image + its licensed source; img: present or MISSING.
AlignFits parent; known overflow/overlay traps flagged.
TimingdurationFrames vs words; anchors ≤ word count.
NeighboursPrevious/next scene; no same-type or same-widget back-to-back.

It runs alongside the hard-budget linter: npm run lint is the pass/fail gate, npm run critique is the qualitative review the director reads before shipping. Both are now referenced in the tech-video-director skill (steps 4 & 6).
